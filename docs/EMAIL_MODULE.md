# Application email module

The new `hq/email_module` package has its own SQLite ledger and an injected Gmail client. It can run and be tested without starting Agent HQ's worker or writing to its main database. `tests/unit/test_email_module.py` exercises an application email, approval, send, reply, interview classification, follow-up, duplicates, and ambiguous delivery with `FakeGmail`. `tests/unit/test_email_module_api.py` exercises the same workflow through authenticated API routes. Run them with:

```sh
.venv/bin/python -m pytest -q tests/unit/test_email_module.py tests/unit/test_email_module_api.py
```

The dashboard is **Application Email** at `/email-module` in Agent HQ. **Sandbox** is the default. Its local fake mailbox and ledger are under `data/email-module/`, separate from `data/hq.db`. Create a contact or import an Agent HQ opportunity ID, add company research, the job description, and a verified experience phrase, then draft, review, approve, and send in the sandbox. The simulated reply control is loopback-only. **Check mail** detects the reply and updates the dashboard. Drafting never sends. Every send needs approval of that exact draft. The module never schedules an automatic send.

The **Gmail** tab uses the existing installed-app OAuth connection in Settings → Gmail. An OAuth grant for `gmail.readonly` allows reading and searching; sending also needs `gmail.send` (the module keeps its own drafts locally, so `gmail.compose` is not required for them). The account returned by Gmail must match the configured owner address. The module's live ledger is `data/email-module/live.db`. Only entries explicitly added or imported into that ledger appear in this dashboard; it does not silently ingest or modify other applications.

Live sends are disabled unless the existing Agent HQ live mode is active and the local process has `HQ_EMAIL_MODULE_LIVE=1`. The module also checks the main pause and outbound freeze switches, requires a separately approved draft, and checks that the recipient matches the verified email on a linked real opportunity. It limits this ledger to ten attempts per UTC day, one send per minute, a 14-day company cooldown for application emails, and at most two follow-ups seven days apart. Replies and terminal statuses cancel follow-ups. Gmail still applies its own account and API limits; these local limits are deliberately lower. Failed or uncertain sends remain in the ledger. An uncertain outcome can be checked against Gmail Sent by the stable Message-ID but is never resent automatically.

The current workspace has no local `.env` Gmail OAuth client or refresh token. A Codex Gmail connector, if available in the chat, does not transfer a token to the locally running Agent HQ app. To run the live module, create your own Google OAuth desktop client, add the client in Settings → Gmail, grant read access, and complete the existing Agent HQ go-live checks before enabling live sends. Google describes scope sensitivity and verification requirements in its [Gmail scope guide](https://developers.google.com/workspace/gmail/api/auth/scopes), and documents current per-user and per-project API quotas in its [quota guide](https://developers.google.com/workspace/gmail/api/reference/quota).

## Connect your own Gmail account

1. Sign in to [Google Cloud Console](https://console.cloud.google.com/) as `sangwanprerit40@gmail.com`, create or select a project, and [enable Gmail API](https://console.cloud.google.com/apis/library/gmail.googleapis.com). Google's [Python quickstart](https://developers.google.com/workspace/gmail/api/quickstart/python) shows the current console flow.
2. In **Google Auth platform → Branding**, configure the consent screen. For a personal Gmail account, choose **External** under **Audience** and add `sangwanprerit40@gmail.com` as a test user. Testing grants can expire after seven days; this is a Google test-mode limit, not an Agent HQ timer. [Google's audience guide](https://support.google.com/cloud/answer/15549945) explains the status.
3. In **Google Auth platform → Clients**, create a client of type **Desktop app** and download its JSON file. Keep that file private. In Agent HQ on this Mac, open **Settings → Gmail**, paste the JSON into its local setup field, then click **Connect sangwanprerit40@gmail.com (read-only)** and consent as that account. Do not put the JSON or refresh token in chat, Git, or a screenshot.
4. Use **Check now** in Gmail settings and **Application Email → Gmail → Check mail** to verify the connection. Search for a known company or application message. Sending access comes later through the existing **Autonomy & Mode** go-live checklist and a new Google consent for send permission. The sandbox can be fully tested before that step.

The new dashboard links main opportunities by ID. A confirmed live send or reply mirrors the opportunity stage and Gmail thread into the main Agent HQ pipeline; sandbox activity never does. Both send paths check the module ledger for daily and company limits. Existing Agent HQ application, inbox and outbound pipelines remain authoritative for automatic job applications. Their own go-live checks and send guard still apply; the email module does not start those workers. The module uses deterministic drafts grounded in the saved context, not an unverified model output. This is the tested baseline for later model-assisted wording with the existing fact gate.
